前六章里，机器人一直是"代码里的一个节点"——没有形状、没有关节、也没有 TF 树。
这一章要做的，是**用一份 URDF/Xacro 文件把机器人"造"出来**，让它能在 RViz 里看见、TF 树能立起来。

| 要解决的问题 | 用什么 |
|---|---|
| 机器人长什么样（连杆、关节、尺寸、颜色） | **URDF** |
| 同样的部件写两遍太蠢（参数化、宏、拆文件） | **Xacro** |
| 模型能不能被物理引擎推动（碰撞体、质量、惯量） | **collision + inertial** |
| 造出来之后怎么才能"会走路" | **导航（Nav2）**——见第 9 节的路线图 |

> 💡 **为什么非做这一步不可**
>
> 后面无论是 Gazebo 仿真还是 Nav2 导航，第一步都是"读一份 URDF，把它变成 TF 树"。
> 没有模型，导航栈连"机器人在哪、朝哪边"都无从谈起——这章就是给后面打地基。

> `ros2 launch ... --show-args` 通过。文中的报错信息也是**实测复现的原文**。

### 1、URDF 的三个角色：robot / link / joint

URDF（Unified Robot Description Format）就是一份 XML，只有三种核心元素：

```
robot  ← 根标签，一个文件一个
 ├── link   ← 连杆/刚体：车体、轮子、雷达、相机……都是 link
 └── joint  ← 关节：连接两个 link，决定它俩怎么动、相距多远
```


**link 是什么**：一块"刚体"，本身不带位置信息。它长什么样由三样东西描述：

| 子标签 | 作用 | 谁在用 |
|---|---|---|
| `<visual>` | 外观（RViz 里看到的） | 显示 |
| `<collision>` | 碰撞形状（物理引擎用的） | 碰撞检测 |
| `<inertial>` | 质量与惯量 | 动力学仿真 |

**joint 是什么**：把两个 link 连起来，并给出**变换关系**。`<parent>` 是父、`<child>` 是子：

```xml
<joint name="imu_joint" type="fixed">
    <origin xyz="0.0 0.0 0.003" rpy="0.0 0.0 0.0"/>  <!-- 子相对父的位姿 -->
    <parent link="base_link"/>
    <child  link="imu_link"/>
</joint>
```


关节类型决定了这个部件"能不能动、怎么动"：

| type | 含义 | 用在哪 |
|---|---|---|
| `fixed` | 焊死，不能动 | 传感器、万向轮 |
| `continuous` | 绕轴无限旋转 | **驱动轮** |
| `revolute` | 绕轴转，但**有角度上下限** | 机械臂关节 |
| `prismatic` | 沿轴平移，有距离上下限 | 升降台、夹爪 |
| `planar` / `floating` | 平面滑动 / 自由浮动 | 很少用 |

> 💡 **知识点：URDF 必须是一棵"树"，不能有环**
>
> 每个 link 只能有**一个**父 joint。原因是 TF 的本质是"每个坐标系相对父坐标系的位姿"——
> 一旦成环，同一个坐标系就有两条计算路径，位姿不再唯一，`robot_state_publisher` 直接罢工。
>
> 所以建模时的常见错误是：两个 link 互相做父子，或者一个轮子被两个 joint 同时"认领"。

### 2、第一个模型：两连杆的 first_robot.urdf

先建一个**普通的功能包**放模型（注意是 `ament_cmake`，因为我们要往 `share/` 里装文件，不用写 Python）：

```bash
ros2 pkg create fishbot_description --build-type ament_cmake --license Apache-2.0
mkdir -p fishbot_description/urdf
```


然后在 `urdf/` 下写第一个模型 `first_robot.urdf`：

```xml
<?xml version="1.0"?>
<robot name="first_robot">
    <!-- ① 车身：一个圆柱 -->
    <link name="base_link">
        <visual>
            <origin xyz="0.0 0.0 0.0" rpy="0.0 0.0 0.0"/>
            <geometry>
                <cylinder radius="0.10" length="0.12"/>
            </geometry>
            <material name="white">
                <color rgba="1.0 1.0 1.0 0.5"/>
            </material>
        </visual>
    </link>

    <!-- ② IMU：一个小方块 -->
    <link name="imu_link">
        <visual>
            <origin xyz="0.0 0.0 0.0" rpy="0.0 0.0 0.0"/>
            <geometry>
                <box size="0.02 0.02 0.02"/>
            </geometry>
            <material name="black">
                <color rgba="0.0 0.0 0.0 1.0"/>
            </material>
        </visual>
    </link>

    <!-- ③ 关节：把 IMU 固定在车身上方 -->
    <joint name="imu_joint" type="fixed">
        <origin xyz="0.0 0.0 0.003" rpy="0.0 0.0 0.0"/>
        <parent link="base_link"/>
        <child link="imu_link"/>
    </joint>
</robot>
```


**`<visual>` 里那三件事，一个都不能少**：

| 标签 | 含义 | 容易踩的坑 |
|---|---|---|
| `<origin xyz rpy>` | 相对**自己几何中心**的偏移和旋转 | 不是绝对坐标！写 `0 0 0` 就是居中对齐 |
| `<geometry>` | 形状：`box` / `cylinder` / `sphere` / `mesh` | 长度单位一律是 **米** |
| `<material>` | 颜色，`rgba` 的 `a` 是**透明度** | 重名 material（如两个 `white`）颜色要一致，否则后定义的说了算 |

> ⚠️ **原稿这里漏了一个 `</link>`**（`imu_link` 的 `</visual>` 之后直接接了 `<joint>`，`<link>` 没闭合）。
> 这是 XML 层面的错误，连"解析"这一步都过不去，实测报错：
>
> ```
> $ check_urdf first_robot.urdf
> Error:   Error=XML_ERROR_MISMATCHED_ELEMENT ErrorID=14 (0xe) Line number=22: XMLElement name=link
>          at line 101 in ./urdf_parser/src/model.cpp
> ERROR: Model Parsing the xml failed
> ```
>
> **教训**：`<link>` 和 `</link>` 要数配对；缩进对齐能救命。

#### 先用工具把结构画出来，再进 RViz

URDF 写完了别急着开 RViz，先用 `urdf_to_graphviz` 把**结构图**打出来看一眼：

```bash
urdf_to_graphviz first_robot.urdf        # 在当前目录生成 <robot_name>.gv 和 .pdf
# 也可以指定输出名（是第二个位置参数，不是 -o）
urdf_to_graphviz first_robot.urdf first_robot_graph
```


```
Created file /tmp/fishbot_graph.gv
Created file /tmp/fishbot_graph.pdf
```


`urdf_to_graphviz` 是对**展开后**的 URDF 做静态分析，比 RViz 快得多——**改完模型先跑它**，
能立刻发现"关节连错、link 名字对不上"这类问题。

### 3、让模型出现在 RViz 里：state publisher + launch

#### 3.1 原理：URDF 是怎么变成画面的

**RViz 自己不读 URDF。** 它只认两样东西：**TF 变换** 和 **话题**。所以中间要有人把模型"翻译"过去：

```
 fishbot.urdf.xacro
        │  xacro 展开（启动时执行）
        ▼
   URDF 文本  ──▶ robot_description（参数）
        │
        │  robot_state_publisher 读取，按关节位置算出每个 link 的位姿
        ▼
   /tf + /tf_static  ──▶ RViz2 的 RobotModel 显示项画出来
        ▲
        │  joint_state_publisher 提供 /joint_states（可动关节的角度）
```


两个发布节点的分工：

| 节点 | 干什么 | 少了它会怎样 |
|---|---|---|
| `robot_state_publisher` | 读 `robot_description`，把每个 link 的位姿算成 TF 发出去 | RViz 里 `RobotModel` 一片空白 + TF 报错 |
| `joint_state_publisher` | 把可动关节的角度发到 `/joint_states` | 轮子等可动关节停在 0 位；`continuous` 关节没有角度来源 |

#### 3.2 装依赖 + 在 package.xml 里声明

```bash
sudo apt install ros-$ROS_DISTRO-robot-state-publisher
sudo apt install ros-$ROS_DISTRO-joint-state-publisher
# 想用滑块手动转轮子，再装这个（调试神器）
sudo apt install ros-$ROS_DISTRO-joint-state-publisher-gui
```


装完还要写进 `package.xml`，否则换台机器就"跑不起来但不知道为啥"：

```xml
<exec_depend>robot_state_publisher</exec_depend>
<exec_depend>joint_state_publisher</exec_depend>
<exec_depend>xacro</exec_depend>
<exec_depend>rviz2</exec_depend>
```


> 💡 **`exec_depend` 是"运行时依赖"**
>
> 模型包不需要编译，所以用 `exec_depend`（运行依赖）而不是 `depend`。
> `rosdep install` 就是照着这些声明去装包的——声明漏了，别人 clone 下来必失败。

#### 3.3 完整的 launch 文件（不是片段）

`launch/display_robot.launch.py`：

```python
import os

import launch
import launch_ros
from ament_index_python.packages import get_package_share_directory


def generate_launch_description():
    # ① 找到这个包的 share 目录：install/fishbot_description/share/fishbot_description
    pkg_share = get_package_share_directory('fishbot_description')
    # 这一版先加载第 2 节那个手写模型；等第 4 节把它宏化之后，这里再改成 .xacro
    default_model_path = os.path.join(pkg_share, 'urdf', 'first_robot.urdf')

    # ② 声明一个可在命令行覆盖的参数：ros2 launch ... model:=/绝对路径/xxx.urdf
    model_arg = launch.actions.DeclareLaunchArgument(
        name='model',
        default_value=default_model_path,
        description='URDF/Xacro 模型的绝对路径')

    # ③ 把模型文件的内容读出来，赋给 robot_description 参数
    #    cat 只适用于"已经是 URDF"的文件；xacro 文件必须换成 xacro 命令（见第 4 节）
    robot_description = launch_ros.parameter_descriptions.ParameterValue(
        launch.substitutions.Command(
            ['cat', launch.substitutions.LaunchConfiguration('model')]),
        value_type=str)

    # ④ 三个节点：关节状态发布、模型状态发布、RViz
    joint_state_publisher_node = launch_ros.actions.Node(
        package='joint_state_publisher',
        executable='joint_state_publisher')

    robot_state_publisher_node = launch_ros.actions.Node(
        package='robot_state_publisher',
        executable='robot_state_publisher',
        parameters=[{'robot_description': robot_description}])

    rviz_node = launch_ros.actions.Node(
        package='rviz2',
        executable='rviz2')

    return launch.LaunchDescription([
        model_arg,
        joint_state_publisher_node,
        robot_state_publisher_node,
        rviz_node,
    ])
```


四步做的事分别是：**找路径 → 声明可覆盖参数 → 把模型内容读进参数 → 起三个节点**。

> 💡 **为什么用 `Command([...])` 而不是在 Python 里 `open()` 读文件**
>
> `Command` 是个"替换"：启动时真正执行那条命令，把 **stdout** 当作参数值。
> 好处是命令执行出错会在 `ros2 launch` 的**启动阶段**就炸出来，而不是等到运行时才报错。
> 这里先用 `cat` 是因为模型还是普通的 `.urdf`；**第 4 节把它宏化之后，就换成 `xacro`**。

> ⚠️ **原稿这三行里藏了三个 API 错误，实测都能复现**：
>
> | 原稿写法 | 正确写法 | 实测报错 |
> |---|---|---|
> | `from ament_index_python.package import ...` | `from ament_index_python.packages import ...` | `ModuleNotFoundError: No module named 'ament_index_python.package'` |
> | `launch.actions.DeclarelaunchArgument` | `launch.actions.DeclareLaunchArgument` | `AttributeError`（**launch 的 L 要大写**） |
> | `launch_ros.parameterValue` | `launch_ros.parameter_descriptions.ParameterValue` | `launch_ros` 里没有 `parameterValue` 这个属性 |
>
> 注意第三行：`ParameterValue` 是 `launch_ros.parameter_descriptions` 模块里的类，
> 正确的导入是 `import launch_ros` 后用全路径 `launch_ros.parameter_descriptions.ParameterValue`。

#### 3.4 CMakeLists.txt：把模型装进 install

launch 里用 `get_package_share_directory` 找的是 **install 目录**，所以必须告诉 CMake 把 `urdf/` 和 `launch/` 拷过去：

```cmake
cmake_minimum_required(VERSION 3.8)
project(fishbot_description)
find_package(ament_cmake REQUIRED)

# 把模型和 launch 文件拷进 install/.../share/fishbot_description/
install(DIRECTORY urdf launch
  DESTINATION share/${PROJECT_NAME}
)

ament_package()
```


> ⚠️ **原稿把 `DESTINATION` 拼成了 `DESTIANTION`**。
> CMake 不认这个关键字，于是"以为你没写目标目录"，实测报错：
>
> ```
> CMake Error at CMakeLists.txt:4 (install):
>   install DIRECTORY given no DESTINATION!
> ```
>
> 报错信息里**没有出现那个拼错的单词**，所以这类错误特别费眼睛——看到 "given no DESTINATION"
> 就要反过来检查是不是拼错了。

编译并运行：

```bash
cd ~/你的工作空间
colcon build --packages-select fishbot_description
source install/setup.bash
ros2 launch fishbot_description display_robot.launch.py
```


**应该看到**：RViz 自动打开（默认配置是空的）→ 左下 `Add` → 加 **RobotModel** → 模型出现在网格上；
再加 **TF** 显示项，能看到每个 link 的坐标轴。

> 💡 **RViz 里看不到模型，先查这三条**（和第六章的排查思路一致）
>
> 1. `ros2 topic echo /robot_description --once` 有没有输出 → 模型读没读进来
> 2. `ros2 param get /robot_state_publisher robot_description` 是不是空
> 3. **Fixed Frame** 有没有设成模型里真实存在的坐标系（比如 `base_link`）——`map` 在这里并不存在

### 4、用 Xacro 消除复制粘贴

上面的 `first_robot.urdf` 只有两个 link 还能忍。真做机器人时，四个轮子、两个 IMU……
**同样的 XML 抄四遍**，改一个尺寸要改四处——这就是 Xacro 存在的理由。

Xacro 是 URDF 的"预处理语言"，加了三样东西：**变量/表达式、宏、文件拆分**。

`urdf/first_robot.urdf.xacro`——其实就是把第 2 节那份手写 URDF 宏化（注意根标签要加 `xmlns:xacro`）：

```xml
<?xml version="1.0"?>
<robot xmlns:xacro="http://www.ros.org/wiki/xacro" name="first_robot">
    <!-- 声明 base 模块：宏 = 带参数的 XML 片段 -->
    <xacro:macro name="base_link" params="length radius">
        <link name="base_link">
            <visual>
                <origin xyz="0 0 0" rpy="0 0 0" />
                <geometry>
                    <cylinder length="${length}" radius="${radius}" />
                </geometry>
                <material name="white">
                    <color rgba="1.0 1.0 1.0 0.5" />
                </material>
            </visual>
        </link>
    </xacro:macro>

    <!-- 声明 IMU 模块：参数不只可以是尺寸，还可以是"名字" -->
    <xacro:macro name="imu_link" params="imu_name xyz">
        <link name="${imu_name}_link">
            <visual>
                <origin xyz="0 0 0" rpy="0 0 0" />
                <geometry>
                    <box size="0.02 0.02 0.02" />
                </geometry>
                <material name="black">
                    <color rgba="0 0 0 0.5" />
                </material>
            </visual>
        </link>
        <joint name="${imu_name}_joint" type="fixed">
            <parent link="base_link" />
            <child link="${imu_name}_link" />
            <origin xyz="${xyz}" />
        </joint>
    </xacro:macro>

    <!-- 传参调用：改尺寸只改这一行 -->
    <xacro:base_link length="0.12" radius="0.1" />
    <!-- 同一个宏调两次，就得到两个 IMU，名字由参数决定 -->
    <xacro:imu_link imu_name="imu_up"   xyz="0 0  0.02" />
    <xacro:imu_link imu_name="imu_down" xyz="0 0 -0.02" />
</robot>
```


三个语法点：

| 写法 | 含义 |
|---|---|
| `<xacro:macro name="X" params="a b">` | 定义宏，`params` 是**空格分隔**的参数名 |
| `${...}` | 表达式，可以做算术：`${length/2.0 + 0.032}` |
| `${imu_name}_link` | 参数可以拼进字符串 → 一个宏生成多个不同名字的 link |

装 xacro：

```bash
sudo apt install ros-$ROS_DISTRO-xacro
```


**把 launch 里的 `cat` 换成 `xacro`**——完整文件如下（对比第 3 节那版，只改了两处：
默认模型指向 `.xacro`、生成方式从 `cat` 换成 `xacro`）：

```python
import os

import launch
import launch_ros
from ament_index_python.packages import get_package_share_directory


def generate_launch_description():
    pkg_share = get_package_share_directory('fishbot_description')
    # 改法 ①：默认模型换成刚写的 .xacro 文件
    default_model_path = os.path.join(pkg_share, 'urdf', 'first_robot.urdf.xacro')

    model_arg = launch.actions.DeclareLaunchArgument(
        name='model',
        default_value=default_model_path,
        description='URDF/Xacro 模型的绝对路径')

    # 改法 ②：生成方式由 cat 改成 xacro —— xacro 会先展开宏、参数和 include
    robot_description = launch_ros.parameter_descriptions.ParameterValue(
        launch.substitutions.Command(
            ['xacro', launch.substitutions.LaunchConfiguration('model')]),
        value_type=str)

    joint_state_publisher_node = launch_ros.actions.Node(
        package='joint_state_publisher',
        executable='joint_state_publisher')

    robot_state_publisher_node = launch_ros.actions.Node(
        package='robot_state_publisher',
        executable='robot_state_publisher',
        parameters=[{'robot_description': robot_description}])

    rviz_node = launch_ros.actions.Node(
        package='rviz2',
        executable='rviz2')

    return launch.LaunchDescription([
        model_arg,
        joint_state_publisher_node,
        robot_state_publisher_node,
        rviz_node,
    ])
```


> ⚠️ **`cat` 和 `xacro` 的区别不是"换个命令"，而是"有没有展开"**
>
> `cat` 把文件**原样**吐出来，模型里的 `${}`、`<xacro:macro>` 一个都不会被处理，
> `robot_state_publisher` 拿到这种文本会直接解析失败（报 XML/URDF 解析错误）。
> **只要文件扩展名是 `.xacro`，就必须用 `xacro` 命令。**

> 💡 **`$(find pkg)` 是 xacro 的子命令，别和 launch 的写法混用**
>
> 在 launch 文件里我们写 `$(find-pkg-share pkg)`，但在 **xacro 文件里必须写 `$(find pkg)`**。
> 实测把 launch 那套抄进 xacro，会直接报错：
>
> ```
> error: ... Unknown substitution command [find-pkg-share fishbot_description].
> Valid commands are ['find', 'env', 'optenv', 'dirname', 'arg']
> ```
>
> xacro 只认这五个子命令：`find` / `env` / `optenv` / `dirname` / `arg`。

### 5、把机器人拆成多个文件：目录结构与 include

一个真实机器人不可能塞在一个文件里。按"部件"拆开，用 `<xacro:include>` 拼装：

```
fishbot_description/
├── CMakeLists.txt
├── package.xml
├── launch/
│   └── display_robot.launch.py
└── urdf/
    ├── first_robot.urdf              # 第 2 节那个"手写版"，留着对照
    └── fishbot/
        ├── common_inertia.xacro      # 惯性公式"零件库"
        ├── base.urdf.xacro           # 车身
        ├── fishbot.urdf.xacro        # ★ 总装文件：include 所有部件并传参调用
        ├── sensor/
        │   ├── imu.urdf.xacro
        │   ├── camera.urdf.xacro
        │   └── laser.urdf.xacro
        └── actuator/
            ├── wheel.urdf.xacro
            └── caster.urdf.xacro
```

### 6、执行器部件：主动轮与万向轮

`actuator/wheel.urdf.xacro`：

```xml
<?xml version="1.0"?>
<robot xmlns:xacro="http://www.ros.org/wiki/xacro">
    <!-- 主动轮：continuous 关节 = 可以连续转的铰链，必须给 axis -->
    <xacro:macro name="wheel_xacro" params="wheel_name xyz">
        <link name="${wheel_name}_wheel_link">
            <visual>
                <!-- 圆柱默认轴是 z，而轮子要绕 y 轴转，所以先把它转 90° -->
                <origin xyz="0.0 0.0 0.0" rpy="1.5707963 0.0 0.0" />
                <geometry>
                    <cylinder radius="0.04" length="0.32" />
                </geometry>
                <material name="yellow">
                    <color rgba="1.0 1.0 0.0 1.0" />
                </material>
            </visual>
        </link>

        <joint name="${wheel_name}_wheel_joint" type="continuous">
            <origin xyz="${xyz}" />
            <parent link="base_link" />
            <child link="${wheel_name}_wheel_link" />
            <axis xyz="0.0 1.0 0.0" />
        </joint>

```xml

    <xacro:macro name="caster_xacro" params="caster_name xyz">
        <link name="${caster_name}_caster_link">
            <visual>

> 💡 **关节类型怎么选（背下来省很多事）**
>
> | 想表达的动作 | type | 必须写的参数 |
> |---|---|---|
> | 驱动轮（能一直转） | `continuous` | `axis`（转轴方向） |
> | 机械臂关节（有角度上限） | `revolute` | `axis` + `limit`（effort/velocity/lower/upper） |
> | 滑轨/升降 | `prismatic` | `axis` + `limit` |
> | 传感器、万向轮 | `fixed` | 不用写 `axis`（写了也没用） |
>
> `wheel` 的 `axis` 是 **y 轴**（左右横穿车身），所以轮子绕 y 轴滚——这与"车头朝 x"的约定一致。

> ⚠️ **两个我发现的问题（原稿未提）**
>
> **① 圆柱体的默认轴是 z，不是 y。** `<cylinder>` 默认沿 z 轴立着。
> 轮子的旋转轴是 y，如果 visual 不做旋转，画面上就是"一根立着的圆桶在绕自己的腰转"。
> 上面的代码给 `<visual>` 加了 `rpy="1.5707963 0 0"`（绕 x 转 90°），让几何轴与转轴对齐。
> 这类"看着不对"的问题 `check_urdf` 查不出来——**只有打开 RViz 用眼睛看**。
>
> **② `length="0.32"` 请核对一下。** 这个值表示轮宽 32cm，而车体直径只有 20cm，
> 轮子会明显宽出车外。我**保留了原值**没动，怀疑是笔误（若原意是 3.2cm，应为 `0.032`）。

### 7、物理属性：collision 与 inertial

到这一步模型"能看"了，但还"推不动"——物理引擎需要两样东西：

| 子标签 | 给谁用 | 不写的后果 |
|---|---|---|
| `<collision>` | 碰撞检测 | 机器人会直接穿过地面/墙壁 |
| `<inertial>` | 动力学（质量、惯量） | Gazebo 里物体乱飞或不受力（没有惯量的 link 在物理引擎里等于没有质量） |

前面第 5.1 节的 `base.urdf.xacro` 已经是**加上物理属性后的完整版本**（原稿在这里分两处写"添加代码"，
一处加 `base_footprint`、一处加 `collision` 和 `inertial`，还都带 `...` 省略号——**本章统一只给最终完整文件**）。
下面补上它引用的"惯性零件库"：

`common_inertia.xacro`：

```xml
<?xml version="1.0"?>
<robot xmlns:xacro="http://www.ros.org/wiki/xacro">
    <!-- 长方体：m 质量、w/h/d 三个边长 -->
    <xacro:macro name="box_inertia" params="m w h d">
        <inertial>
            <mass value="${m}" />
            <inertia ixx="${(m/12) * (h*h + d*d)}" ixy="0.0" ixz="0.0"
                     iyy="${(m/12) * (w*w + d*d)}" iyz="0.0"
                     izz="${(m/12) * (w*w + h*h)}" />
        </inertial>
    </xacro:macro>

    <!-- 圆柱：m 质量、r 半径、h 高（轴沿 z） -->
    <xacro:macro name="cylinder_inertia" params="m r h">
        <inertial>
            <mass value="${m}" />
            <inertia ixx="${(m/12) * (3*r*r + h*h)}" ixy="0" ixz="0"
                     iyy="${(m/12) * (3*r*r + h*h)}" iyz="0"
                     izz="${(m/2) * (r*r)}" />
        </inertial>
    </xacro:macro>

    <!-- 球：m 质量、r 半径 -->
    <xacro:macro name="sphere_inertia" params="m r">
        <inertial>
            <mass value="${m}" />
            <inertia ixx="${(2/5) * m * (r*r)}" ixy="0.0" ixz="0.0"
                     iyy="${(2/5) * m * (r*r)}" iyz="0.0"
                     izz="${(2/5) * m * (r*r)}" />
        </inertial>
    </xacro:macro>
</robot>
```


> 💡 **这些公式是哪来的（看懂就不用背）**
>
> `<inertia>` 是一个 3×3 的**惯性张量**，对角线上是绕三个轴的转动惯量 `ixx/iyy/izz`。
> 表达式就是大学物理那几个公式：
>
> | 形状 | 绕 z 轴（`izz`） | 绕 x/y 轴 |
> |---|---|---|
> | 长方体（w×h×d） | `m(w²+h²)/12` | `m(h²+d²)/12`、`m(w²+d²)/12` |
> | 实心圆柱（半径 r、高 h） | `m·r²/2`（**与高度无关**） | `m(3r²+h²)/12` |
> | 实心球 | `2mr²/5` | 同左（球对称） |
>
> 所以 `cylinder_inertia` 里的 `izz="${(m/2)*(r*r)}"` 就是 `½mr²`——
> **转动惯量只跟质量分布有关**，跟颜色、外观没关系。
>
> 非对角项 `ixy/ixz/iyz` 是"惯性积"，只有当物体相对坐标轴**倾斜**时才不为 0；
> 我们的部件都正着放，所以一律填 `0`。

> ⚠️ **原稿的两个物理属性问题**
>
> **① `<collision>` 里不能放 `<material>`。** URDF 规范里材质属于 `<visual>`，原稿把
> `<material>` 抄进了 `<collision>`。本次修正为：collision 只保留 `<origin>` + `<geometry>`。
>
> **② collision 与 visual 的形状要一致。** 原稿 collision 里写的是
> `<cylinder length="${length}" radius="${length}" />`——`radius` 误写成了 `length`
> （0.12 的半径比车体还大）。这类错误**不会报错**，但物理世界里的碰撞体和看到的样子完全不是一回事，
> 排查起来极其痛苦。**改尺寸时记得 visual / collision 两处同步改。**

> 💡 **`base_footprint` 是什么，为什么要有它**
>
> 它是车身在**地面上的投影点**（z 恒为 0），`base_link` 则挂在它上面、抬高半个车体。
> 好处是：导航和定位算法都希望机器人的"根坐标系"**贴着地面**，
> 这样"机器人位姿"就等于"地面上的位置 + 朝向"，不用管内部分配的高度。
>
> Nav2 默认期待 `base_footprint`（或 `base_link`）在 `odom` 下面——第 9 节会接着讲。

### 9、在 Gazebo 中完成机器人仿真

> ✅ **本节验证环境**：Ubuntu 24.04 + ROS 2 Jazzy + **Gazebo Harmonic（gz-sim 8.15.0）**。
> 下面的话题名全部抄自本机 `gz topic -l` 的真实输出，URDF 生成进 Gazebo 也实跑通过
> （`[ros_gz_sim]: Entity creation successful.`）。
>
> 原书基于 **ROS 2 Humble + Gazebo Classic**，那套命令在 Jazzy 上**整条作废**——
> 而且不是"包名换一下"就行，是**插件体系整个换了**（见 9.1）。

#### 9.1 仿真到底在仿什么，用哪个仿真器

机器人的最小闭环是 **传感器 → 控制系统 → 执行器**，环境给传感器提供输入：

```
   环境  ──▶  传感器  ──▶  控制系统  ──▶  执行器  ──▶  环境
  （场景）              （算/judge）          （轮子…）
```


对仿真来说，"控制系统"本来就是软件，所以真正要仿的是**传感器、执行器、环境**这三样。

| 仿真平台 | 特点 | 本机情况 |
|---|---|---|
| **Gazebo Classic**（gazebo11） | 老书 / 老教程用的就是它，ROS 支持最友好、资料最多 | ❌ **2025 年 1 月已 EOL**，官方不出 Ubuntu 24.04（noble）的包。本机敲 `gazebo` 就是 `未找到命令` |
| **Gazebo Harmonic**（新 Gazebo / gz-sim 8） | Classic 的官方接班人，ROS 2 Jazzy 的搭配 | ✅ 本机已装：`gz sim --version` → **8.15.0** |
| Webots | 跨平台、开箱即用的模型多 | 需另装 |
| CoppeliaSim | 前身 V-REP，多平台多语言 | 需另装 |
| Unity 3D / MATLAB Simulink | 通用引擎 / 工具链 | 需额外桥接 |

> ⚠️ **本节总纲：Harmonic 不再把 ROS 插件塞进仿真器**
>
> Gazebo Classic 的思路是"把 ROS 插件 `dlopen` 进 gazebo 进程"：所以有
> `libgazebo_ros_diff_drive.so`、`libgazebo_ros_camera.so` 这些库，机器人一加载，
> ROS 2 话题就自己冒出来了。
>
> **Harmonic 完全不是这样。** 仿真器只认自己的 **gz-transport** 话题，跟 ROS 2 没有任何关系；
> 要让 ROS 2 看见数据，必须**显式起一个桥**（`ros_gz_bridge`）把两边话题对接起来。
> 这个变化是本节所有命令差异的根源：

| 要做的事 | Humble + Classic（书） | **Jazzy + Harmonic（本笔记）** |
|---|---|---|
| 启动仿真器 | `gazebo` | **`gz sim`**（是 `gz` 的**子命令**，不是独立命令） |
| ROS 桥接包 | `ros-humble-gazebo-ros` | **`ros-jazzy-ros-gz`** |
| 生成机器人 | `ros2 run gazebo_ros spawn_entity.py` | **`ros2 run ros_gz_sim create`** |
| 差速驱动 | `libgazebo_ros_diff_drive.so` | **`gz-sim-diff-drive-system`**（gz 原生插件） |
| 传感器出话题 | `libgazebo_ros_camera.so` 等直接发 ROS 话题 | 传感器只发 **gz 话题**，再用 `parameter_bridge` 桥到 ROS |
| ros2_control 桥 | `libgazebo_ros2_control.so` | **`gz_ros2_control-system`** |
| 世界文件 | `.world` | `.sdf`（内容本来都是 SDF，只是扩展名习惯不同） |

> 💡 一句话记法：
> **Classic 是"Gazebo 里长出了 ROS"；Harmonic 是"Gazebo 和 ROS 各说各话，中间架桥"。**

#### 9.2 装 Gazebo、建世界、启动

```bash

>

>
> **一句话：任何终端跑仿真之前，先 `source /opt/ros/jazzy/setup.bash`。**

> ⚠️ **别指望 `gazebo` 这个命令**
>
> 它在 Ubuntu 24.04 上不存在，官方也不再提供（Classic 已 EOL）。
> 看到 `gazebo：未找到命令` 不是环境坏了，是**该换命令了**。

**建世界**：Harmonic 用 **SDF**，`gz sim` 直接吃 `.sdf`。

放进 launch 时注意：**`ros_gz_sim` 的 `gz_sim.launch.py` 没有 `world` 参数**，

`gz_args`、`gz_version`、`ign_args`、`ign_version`、`debugger`、`debug_env`）：

```python

```


```cmake

```


启动后自检（**Harmonic 时代最重要的排查动作**）：

```bash
gz topic -l                    # 仿真器里现在有哪些话题
gz service -l                  # 有哪些服务
gz topic -e -t /clock -n 1     # 看一眼仿真时间在不在走
```


> 💡 **为什么先查 gz 话题，而不是 `ros2 topic list`**
>
> 因为 Harmonic 里仿真器侧和 ROS 侧是**两套独立的话题空间**。机器人不动时，排查顺序永远是：
>
> 1. **gz 侧有没有数据**（`gz topic -l` / `gz topic -e`）
> 2. gz 侧有、ROS 侧没有 → **问题一定在桥上**（桥没起 / 话题名或消息类型写错）
> 3. gz 侧就没有 → 问题在模型或世界文件（插件没挂上 / 少了 `Sensors` 插件）

#### 9.3 把机器人放进 Gazebo：`ros_gz_sim create`

Harmonic 里"生成实体"由 `ros_gz_sim` 的 **`create`** 负责（不再是 `spawn_entity.py`）。
本机 `--help` 实测的参数：

```
create -world [arg] [-file FILE] [-topic TOPIC] [-param PARAM] [-string STRING]
       [-name NAME] [-allow_renaming] [-x X] [-y Y] [-z Z] [-R R] [-P P] [-Y Y]
```


对 URDF 机器人，标准姿势是**让 `robot_state_publisher` 把模型发到 `/robot_description`，
再让 `create` 去订阅这个参数**：

```bash
# 终端 A：起仿真器（世界名默认就是 default）
gz sim -r 你的世界.sdf

# 终端 B：把 xacro 展开并发布到 /robot_description
ros2 run robot_state_publisher robot_state_publisher --ros-args \
  -p robot_description:="$(xacro 模型.urdf.xacro)"

# 终端 C：从 /robot_description 取模型生成进世界
ros2 run ros_gz_sim create -world default -topic robot_description -name fishbot -z 0.1
```


也可以绕开话题、直接读文件（本机就是用这条验证通过的）：

```bash
ros2 run ros_gz_sim create -world default -file /tmp/fishbot.urdf -name fishbot -z 0.1
# [INFO] [ros_gz_sim]: Entity creation successful.
```


> 💡 `-topic robot_description` 和 `-file` 二选一：
> `-topic` 的好处是改了模型只要重发参数；`-file` 适合一次性验证。
> `-x/-y/-z` 是初始位置，`-R/-P/-Y` 是初始姿态（**弧度**）。
> 机器人一出生就悬空掉下来、或者卡在地里抖，基本都是这几个值没给对。
>
> ⚠️ 顺带一提：`robot_state_publisher <文件.urdf>` 这种"直接跟一个文件路径"的写法
> **能用但已弃用**（本机实测会打印 `This backwards compatibility fallback will be removed
> in the future`）。正经写法是上面用 `-p robot_description:=` 传参数。

把整套写成一个 launch：

```python
import os

from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription
from launch.launch_description_sources import PythonLaunchDescriptionSource
from launch.substitutions import Command
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue


def generate_launch_description():
    pkg_share = get_package_share_directory('fishbot_description')

    xacro_file = os.path.join(pkg_share, 'urdf', 'fishbot.urdf.xacro')
    world_file = os.path.join(pkg_share, 'world', 'fishbot.sdf')
    robot_description = ParameterValue(Command(['xacro ', xacro_file]), value_type=str)

    # ① 启动 Gazebo Harmonic 并加载世界（世界是通过 gz_args 传的）
    gz_sim = IncludeLaunchDescription(
        PythonLaunchDescriptionSource(
            os.path.join(get_package_share_directory('ros_gz_sim'),
                         'launch', 'gz_sim.launch.py')),
        launch_arguments={'gz_args': '-r ' + world_file}.items())

    # ② URDF -> /robot_description
    robot_state_publisher = Node(
        package='robot_state_publisher',
        executable='robot_state_publisher',
        parameters=[{'robot_description': robot_description,
                     'use_sim_time': True}],
        output='screen')

    # ③ 从 /robot_description 生成机器人
    spawn = Node(
        package='ros_gz_sim',
        executable='create',
        arguments=['-world', 'default',
                   '-topic', 'robot_description',
                   '-name', 'fishbot',
                   '-z', '0.1'],
        output='screen')

    rviz = Node(package='rviz2', executable='rviz2',
                parameters=[{'use_sim_time': True}], output='screen')

    return LaunchDescription([gz_sim, robot_state_publisher, spawn, rviz])
```


> ⚠️ **顺序坑**：launch 里的 Action 默认并行，`create` 可能比 Gazebo 先就绪而报"连不上服务"。
> 要么用 `RegisterEventHandler` + `OnProcessExit` 串行化（§10.4 会用到），
> 要么**第一次调模型时干脆分终端手动起**——报错看得最清楚。

#### 9.4 用 `<gazebo>` 标签给模型补"仿真专用"信息

`<gazebo>` 是**写给仿真器看的**标签（URDF 标准里没有它，`check_urdf` 也不管）。
`reference="xxx_link"` 表示"下面这些配置作用于哪个 link"。

**① 改颜色**（`laser.urdf.xacro` 的宏里追加）：

```xml
<gazebo reference="laser_cylinder_link">
    <material>Gazebo/Black</material>
</gazebo>
<gazebo reference="laser_link">
    <material>Gazebo/Black</material>
</gazebo>
```


颜色名用 Gazebo 内置的（`Gazebo/Black`、`Gazebo/Blue`、`Gazebo/Red`、`Gazebo/Green`…），
不是 RGBA，和 `<material><color rgba=...>` 是两套东西。

**② 改摩擦（轮胎要有抓地力）**（`wheel.urdf.xacro` 的宏里追加）：

```xml
<gazebo reference="${wheel_name}_wheel_link">
    <mu1 value="20.0"/>
    <mu2 value="20.0"/>
    <kp value="1000000000.0"/>
    <kd value="1.0"/>
</gazebo>
```


**③ 万向轮要"零摩擦"**（`caster.urdf.xacro` 的宏里追加）：

```xml
<gazebo reference="${caster_name}_caster_link">
    <mu1 value="0.0"/>
    <mu2 value="0.0"/>
    <kp value="1000000000.0"/>
    <kd value="1.0"/>
</gazebo>
```


| 参数 | 含义 | Gazebo 默认值 |
|---|---|---|
| `mu1` | 切向（滑动）摩擦系数 | 1.0 |
| `mu2` | 法向（滚动）摩擦系数 | 1.0 |
| `kp` | 接触刚度 | 1e12 |
| `kd` | 接触阻尼 | 1.0 |

> 💡 **这两组摩擦为什么要反着设**
>
> 主动轮是橡胶胎，摩擦力不够就**原地打滑、里程计乱飘**，所以 `mu1/mu2` 提到 20；
> 万向轮只负责"撑住车"，如果它也有摩擦，转弯时会和主动轮**互相别着**，机器人走不直——所以设成 0。

> 💡 **这些标签在 Harmonic 里是怎么生效的**
>
> URDF 本身没有 `<gazebo>`；是 sdformat 在 **URDF → SDF** 转换时才把它翻译成
> SDF 的 `<material>` / `<surface><friction>`。所以：
>
> - **只有"被生成进 Gazebo"时它们才起作用**——`check_urdf` 和 RViz 完全不看；
> - 物理参数写错了 `check_urdf` **永远查不出来**，只能在仿真里观察行为（打滑、走不直）。

#### 9.5 两轮差速：`gz-sim-diff-drive-system`

Harmonic 的差速驱动是 **gz 原生插件**，不是 ROS 插件。它的输入输出都是 **gz 话题**：

```
                       配置参数（轮距 / 轮半径 / 关节名）
                                │
  /model/fishbot/cmd_vel ──▶ gz-sim-diff-drive-system ──▶ /model/fishbot/odometry
     （gz 话题，要桥接）              （gz 原生插件）        └─▶ /model/fishbot/tf
                                                              （odom → base_footprint）
```


> 💡 注意"目标 ≠ 实际"：你发的是**目标速度**，插件回读的是 Gazebo 里的**实际速度**。
> 轮子被墙卡住时，你发多大的目标速度，实际速度都是 0——这正是仿真比真机好排查的地方。

**完整插件文件** `urdf/fishbot/plugins/gazebo_control_plugin.xacro`
（注意 `filename` 和 `name` 都换了，也**不再有 `<ros><remapping>`**——那是 Classic 的写法）：

```xml
<?xml version="1.0"?>
<robot xmlns:xacro="http://www.ros.org/wiki/xacro">
    <xacro:macro name="gazebo_control_plugin">
        <gazebo>
            <plugin filename="gz-sim-diff-drive-system"
                    name="gz::sim::systems::DiffDrive">
                <left_joint>left_wheel_joint</left_joint>
                <right_joint>right_wheel_joint</right_joint>

                <!-- 运动学：轮距与轮半径，正逆解和里程计都靠它俩 -->
                <wheel_separation>0.2</wheel_separation>
                <wheel_radius>0.032</wheel_radius>

                <odom_publish_frequency>30</odom_publish_frequency>

                <!-- 限幅 -->
                <max_linear_acceleration>1.0</max_linear_acceleration>
                <min_linear_acceleration>-1.0</min_linear_acceleration>
                <max_angular_acceleration>2.0</max_angular_acceleration>
                <min_angular_acceleration>-2.0</min_angular_acceleration>
                <max_linear_velocity>0.5</max_linear_velocity>
                <min_linear_velocity>-0.5</min_linear_velocity>
                <max_angular_velocity>1.0</max_angular_velocity>
                <min_angular_velocity>-1.0</min_angular_velocity>
            </plugin>
        </gazebo>
    </xacro:macro>
</robot>
```


| 配置项 | 含义 |
|---|---|
| `left_joint` / `right_joint` | 左右轮关节名（**必须和 URDF 里一致**） |
| `wheel_separation` | 轮距 |
| **`wheel_radius`** | **轮半径**。⚠️ Classic 写的是 `wheel_diameter`（轮径），这里换成了半径——**填错里程计直接差一倍** |
| `odom_publish_frequency` | 里程计发布频率（Hz） |
| `max_*` / `min_*` | 速度、加速度限幅 |

在总装文件里引入并调用：

```xml
<xacro:include filename="$(find fishbot_description)/urdf/fishbot/plugins/gazebo_control_plugin.xacro" />
<xacro:gazebo_control_plugin />
```


**生成后 gz 侧会自动出现这些话题**（本机实测输出，模型名 `fishbot`）：

| gz 话题 | 方向 | 说明 |
|---|---|---|
| `/model/fishbot/cmd_vel` | 订阅 | 把目标速度发给它 |
| `/model/fishbot/odometry` | 发布 | 里程计 |
| `/model/fishbot/tf` | 发布 | `odom → base_footprint` |
| `/model/fishbot/enable` | 订阅 | 使能开关 |

```bash
gz topic -l | grep fishbot      # 本机实测就是上面这四个
```


**桥到 ROS**——用 `remappings` 映射成 ROS 里通用的 `/cmd_vel`、`/odom`、`/tf`：

```python
Node(
    package='ros_gz_bridge',
    executable='parameter_bridge',
    arguments=[
        '/clock@rosgraph_msgs/msg/Clock[gz.msgs.Clock',                    # gz -> ROS
        '/model/fishbot/cmd_vel@geometry_msgs/msg/Twist]gz.msgs.Twist',    # ROS -> gz
        '/model/fishbot/odometry@nav_msgs/msg/Odometry[gz.msgs.Odometry',  # gz -> ROS
        '/model/fishbot/tf@tf2_msgs/msg/TFMessage[gz.msgs.Pose_V',         # gz -> ROS
    ],
    remappings=[
        ('/model/fishbot/cmd_vel', '/cmd_vel'),
        ('/model/fishbot/odometry', '/odom'),
        ('/model/fishbot/tf', '/tf'),
    ],
    parameters=[{'use_sim_time': True}],
    output='screen')
```


> 💡 **桥接参数的方向符（本机 `parameter_bridge --help` 原文）**
>
> ```
> @  == a bidirectional bridge
> [  == a bridge from Gazebo to ROS
> ]  == a bridge from ROS to Gazebo
> ```
>
> 写法是 `<话题>@<ROS类型><方向符><gz类型>`。
> **方向写反不会报错，只是数据单向流不动**——很隐蔽：
> `/cmd_vel` 必须是 `]`（ROS→gz），`/odom` 必须是 `[`（gz→ROS）。
>
> 另外注意 `/model/fishbot/tf` 的 **gz 类型是 `gz.msgs.Pose_V`**，不是 `TFMessage`。

> 表现就是"话题明明有数据，RViz 里却没有坐标系"。

> 并且 `gz topic -e -t /imu -n 1` 能读到真实数据。

|---|---|---|

> 所以上面相机那两行是注释掉的，不要照抄猜的名字。

### 10、用 ros2_control 驱动机器人

#### 10.1 为什么需要 ros2_control

Gazebo 的两轮差速插件里有**两件事**：

```
        ┌───────────────── gz-sim-diff-drive-system ────────────────┐
        │  ① 数据接口：从 Gazebo 读轮速、往 Gazebo 写目标速度        │
        │  ② 控制器  ：根据轮速算里程计 + 根据 cmd_vel 算目标轮速    │
        └────────────────────────────────────────────────────────────┘
```


搬到真机上时，① 必须重写（要对接真实电机和编码器），但 ② **完全一样**——
这就是"重复造轮子"的地方。ros2_control 的思路：**把控制器抽出来，让仿真和真机共用同一套控制器**，
前提是先把"数据接口"标准化。

```
                  ┌──────────┐   ┌──────────┐   ┌──────────┐
                  │ 控制器 A │   │ 控制器 B │   │ 控制器 C │   ← 可插拔
                  └────┬─────┘   └────┬─────┘   └────┬─────┘
                       └─────── 控制器管理器 ────────┘
                                   │  授予/占用接口
                            接口管理器
                     ┌─────────────┼─────────────┐
              状态接口(只读)   命令接口(读写)
                     └─────────────┼─────────────┘
                  ┌──────────┬─────┴─────┬──────────┐
                  │  传感器  │   执行器   │   系统    │  ← 硬件资源（Gazebo 或真机）
                  └──────────┴───────────┴──────────┘
```


> 💡 三个关键概念
>
> - **硬件资源**分三类：**传感器**（只读）、**执行器**（能读能写）、**系统**（既有传感器又有执行器的复合设备，比如机械臂）
> - **接口**分两种：**状态接口**（只读，position/velocity/effort）、**命令接口**（可写，同一时刻**只能被一个控制器占用**）
> - **控制器管理器**：负责加载/激活/切换控制器。想象两个控制器一个让轮子正转一个反转——接口独占就是为了防止这种事

#### 10.2 安装与命令行

```bash
sudo apt install ros-$ROS_DISTRO-ros2-control
ros2 control --help            # 列出的都是对硬件接口和控制器的操作
ros2 control list_controller_types   # 看系统里有哪些控制器类型

# 常用控制器都收在这个元包里
sudo apt info ros-$ROS_DISTRO-ros2-controllers
sudo apt install ros-$ROS_DISTRO-ros2-controllers
```


常用的控制器：`diff_drive_controller/DiffDriveController`（两轮差速）、
`joint_state_broadcaster/JointStateBroadcaster`（发布关节状态）、
`effort_controllers/JointGroupEffortController`（力控）、`.../JointTrajectoryController`（轨迹）等。

> 💡 `ros2 control` 这一族命令**底层也是服务**，和 `ros2 param` 一个套路。
> 所以 Gazebo 没起来时随便敲一条，会直接告诉你"连不上服务"——这反而是最快的自检。

#### 10.3 把 Gazebo 接进 ros2_control

```bash

```


> ⚠️ **Harmonic 和 Classic 的差异就三处，但每处都得改**
>
> | | Classic（书） | **Harmonic（本笔记）** |
> |---|---|---|
> | `<hardware>` 里的插件 | `gazebo_ros2_control/GazeboSystem` | **`gz_ros2_control/GazeboSimSystem`** |
> | `<gazebo>` 插件 filename | `libgazebo_ros2_control.so` | **`libgz_ros2_control-system.so`** |
> | `<gazebo>` 插件 name | `gazebo_ros2_control` | **`gz_ros2_control::GazeboSimROS2ControlPlugin`** |
>
> 名字记混会报"找不到 shared library"——因为 `gz_ros2_control` 是**独立仓库**
> （`ros-controls/gz_ros2_control`），不是 `gazebo_ros` 的一部分。

**第一步：用 `<ros2_control>` 标签描述硬件资源**——新建 `urdf/fishbot/fishbot.ros2_control.xacro`：

```xml
<?xml version="1.0"?>
<robot xmlns:xacro="http://www.ros.org/wiki/xacro">
    <xacro:macro name="fishbot_ros2_control">
        <ros2_control name="FishBotGazeboSystem" type="system">
            <hardware>
                <!-- 用 Gazebo 当硬件：这一行是 Harmonic 的写法 -->
                <plugin>gz_ros2_control/GazeboSimSystem</plugin>
            </hardware>

            <joint name="left_wheel_joint">
                <command_interface name="velocity">
                    <param name="min">-1</param>
                    <param name="max">1</param>
                </command_interface>
                <command_interface name="effort">
                    <param name="min">-0.1</param>
                    <param name="max">0.1</param>
                </command_interface>
                <state_interface name="position"/>
                <state_interface name="velocity"/>
                <state_interface name="effort"/>
            </joint>

            <joint name="right_wheel_joint">
                <command_interface name="velocity">
                    <param name="min">-1</param>
                    <param name="max">1</param>
                </command_interface>
                <command_interface name="effort">
                    <param name="min">-0.1</param>
                    <param name="max">0.1</param>
                </command_interface>
                <state_interface name="position"/>
                <state_interface name="velocity"/>
                <state_interface name="effort"/>
            </joint>
        </ros2_control>
    </xacro:macro>
</robot>
```


> 💡 **关节名必须和 URDF 里的一致**——ros2_control 是靠关节名把"接口"和"模型里的关节"对上的。
> 两个轮子各给了 2 个命令接口（速度/力）+ 3 个状态接口（位置/速度/力），
> **命令接口带 `min`/`max` 限幅**，这也是仿真的价值之一：真机上超限会烧电机，这里只是被限住。

**第二步：让 Gazebo 加载 gz_ros2_control 插件并读这个配置文件**——在同一个文件里追加：

```xml
<gazebo>
    <plugin filename="libgz_ros2_control-system.so"
            name="gz_ros2_control::GazeboSimROS2ControlPlugin">
        <parameters>$(find fishbot_description)/config/fishbot_ros2_controller.yaml</parameters>
    </plugin>
</gazebo>
```


**第三步：写控制器配置文件** `config/fishbot_ros2_controller.yaml`：

```yaml
controller_manager:
  ros__parameters:
    update_rate: 100          # Hz，控制器管理器刷新率
    use_sim_time: true        # 用 Gazebo 的仿真时间（/clock），不写会让 TF 时间戳对不上
```


（三个控制器在 10.4 里逐个往这个文件里加）

**第四步：在总装文件里切换控制方式**——注意
**两轮差速插件和 ros2_control 不能同时生效**（会抢同一批关节）：

```xml
<!-- <xacro:gazebo_control_plugin/> -->          <!-- 用 ros2_control 时把它注释掉 -->
<xacro:include filename="$(find fishbot_description)/urdf/fishbot/fishbot.ros2_control.xacro"/>
<xacro:fishbot_ros2_control/>
```


启动后 Gazebo 侧应当打出这些日志：

```

[gz_ros2_control]: connected to service!! robot_state_publisher
[resource_manager]: Successful
```

#### 10.4 三个控制器：状态发布 / 力控 / 两轮差速

**① joint_state_broadcaster：先把轮子的 TF 补回来**

> ⚠️ **典型现象**：注释掉两轮差速插件、改用 ros2_control 后，RViz 里两个轮子**变成白色**。
> 原因不是模型坏了，而是**没有节点发布"轮子 → base_footprint"的 TF 了**。
> 补它的正是 joint_state_broadcaster。

`config/fishbot_ros2_controller.yaml` 追加：

```yaml
fishbot_joint_state_broadcaster:
  type: joint_state_broadcaster/JointStateBroadcaster
```


它是**靠命令行或 launch 来加载激活**的：

```bash
ros2 control load_controller fishbot_joint_state_broadcaster --set-state active
# Sucessfully loaded controller fishbot_joint_state_broadcaster into state active
ros2 control list_controllers        # 看状态是不是 active
```


加载后它会把**所有状态接口**用 `/joint_states` 发出来，`robot_state_publisher` 再转成 TF，
RViz 里轮子就恢复显示了。

不想每次手敲，就写进 launch——**关键是"等机器人加载完再激活控制器"**。
下面是完整的 `gazebo_sim.launch.py`（在第 9 节那份的基础上，加了事件处理器自动加载控制器）：

```python
import os

from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription, RegisterEventHandler
from launch.event_handlers import OnProcessExit
from launch.launch_description_sources import PythonLaunchDescriptionSource
from launch.substitutions import Command
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue


def generate_launch_description():
    pkg_share = get_package_share_directory('fishbot_description')

    xacro_file = os.path.join(pkg_share, 'urdf', 'fishbot.urdf.xacro')
    world_file = os.path.join(pkg_share, 'world', 'fishbot.sdf')
    robot_description = ParameterValue(Command(['xacro ', xacro_file]), value_type=str)

    # ① 启动 Gazebo Harmonic（世界通过 gz_args 传）
    gz_sim = IncludeLaunchDescription(
        PythonLaunchDescriptionSource(
            os.path.join(get_package_share_directory('ros_gz_sim'),
                         'launch', 'gz_sim.launch.py')),
        launch_arguments={'gz_args': '-r ' + world_file}.items())

    # ② URDF -> /robot_description
    robot_state_publisher_node = Node(
        package='robot_state_publisher',
        executable='robot_state_publisher',
        parameters=[{'robot_description': robot_description,
                     'use_sim_time': True}],
        output='screen')

    # ③ 生成机器人
    spawn_entity_node = Node(
        package='ros_gz_sim',
        executable='create',
        arguments=['-world', 'default', '-topic', 'robot_description',
                   '-name', 'fishbot', '-z', '0.1'],
        output='screen')

    rviz_node = Node(package='rviz2', executable='rviz2',
                     parameters=[{'use_sim_time': True}], output='screen')

    # ④ 加载并激活 joint_state_broadcaster
    #    推荐用 controller_manager 的 spawner，它自己会等控制器管理器就绪
    load_joint_state_controller = Node(
        package='controller_manager',
        executable='spawner',
        arguments=['fishbot_joint_state_broadcaster'],
        output='screen')

    return LaunchDescription([
        gz_sim,
        robot_state_publisher_node,
        spawn_entity_node,
        rviz_node,

        # ⑤ 事件动作：create 退出（机器人已生成）之后，再加载控制器
        RegisterEventHandler(
            event_handler=OnProcessExit(
                target_action=spawn_entity_node,
                on_exit=[load_joint_state_controller],
            )),
    ])
```


> 💡 launch 里 Action 是**并行**的，而"控制器激活"必须在"机器人生成"之后。
> `RegisterEventHandler` + `OnProcessExit` 就是官方的串行化手段——控制器一多，顺序更重要，
> 否则会互相抢服务接口导致启动异常。

**② 力控制器（effort controller）：给轮子施加力矩**

```yaml
fishbot_effort_controller:
  type: effort_controllers/JointGroupEffortController

fishbot_effort_controller:
  ros__parameters:
    joints:
      - left_wheel_joint
      - right_wheel_joint
    command_interfaces:
      - effort
    state_interfaces:
      - position
      - velocity
      - effort
```


```bash

```

**③ 两轮差速控制器：仿真/真机通用的那个"轮子之外的大脑"**

```yaml
fishbot_diff_drive_controller:
  type: diff_drive_controller/DiffDriveController

fishbot_diff_drive_controller:
  ros__parameters:
    left_wheel_names: ["left_wheel_joint"]
    right_wheel_names: ["right_wheel_joint"]
    wheel_separation: 0.20        # 轮距（m）
    wheel_radius: 0.032           # 轮半径（m）
    wheel_separation_multiplier: 1.0
    left_wheel_radius_multiplier: 1.0
    right_wheel_radius_multiplier: 1.0
    publish_rate: 50.0
    odom_frame_id: odom
    base_frame_id: base_footprint
    pose_covariance_diagonal: [0.001, 0.001, 0.0, 0.0, 0.0, 0.01]
    twist_covariance_diagonal: [0.001, 0.0, 0.0, 0.0, 0.0, 0.01]
    open_loop: true
    enable_odom_tf: true
    cmd_vel_timeout: 0.5
    use_stamped_vel: false
```


| 参数 | 作用 | 注意 |
|---|---|---|
| `left/right_wheel_names` | 两个驱动轮关节名 | 必须与 URDF 一致 |
| `wheel_separation` / `wheel_radius` | 轮距 / 轮半径 | **量错就里程计漂移**，与插件里的值保持一致 |
| `open_loop` | 是否开环（不依赖轮速反馈直接积分） | 仿真里常设 `true` |
| `enable_odom_tf` | 是否发布 `odom→base_footprint` | 导航必须要它 |
| `cmd_vel_timeout` | 多久没收到 `/cmd_vel` 就停车 | 安全兜底 |
| `use_stamped_vel` | 速度指令是否带时间戳 | `false` = 收 `Twist`；`true` = `TwistStamped` |

加载它之后，`/cmd_vel` 的订阅者和 `/odom` 的发布者就都回来了，效果和 Gazebo 差速插件一样，
但**这套控制器换到真机上不用重写**——这就是 10.1 节说的"不重复造轮子"。

### 11、导航总览：SLAM 与 Nav2 分别解决什么

> ⚠️ **来源与验证程度**：本机未安装 `nav2` / `slam_toolbox`（`ros2 pkg list` 里搜不到），
> 所以本章导航部分**未在本机实跑**，按《ROS2机器人开发：从入门到实践》第 7 章整理；
> 书中给出的终端输出我都标了"（书中实测）"。

#### 11.1 两个问题：我在哪 + 怎么去

| 问题 | 谁来解决 | 关键技术 |
|---|---|---|
| 环境长什么样？我在哪？ | **SLAM**（同步定位与地图构建） | 激光扫描匹配 + 位姿图优化（`slam_toolbox`） |
| 已知地图，我怎么走过去？ | **Nav2**（Navigation 2） | 代价地图 + 全局/局部规划 + 控制 |

**SLAM**（Simultaneous Localization and Mapping）就是"边走边画图，同时估计自己的位置"：

```
 激光 /scan ──┐
              ├──▶ SLAM 节点 ──▶ /map（栅格地图）
 里程计 TF ────┘        │
                        └──▶ map→odom 变换（修正里程计漂移）
```


**地图**是"栅格占用地图"（occupancy grid）：每个格子有一个"被占据的概率"。

| 颜色 | 含义 |
|---|---|
| 白色 | 可通行（free） |
| 黑色 | 障碍物（occupied） |
| 灰色 | 未知区域（unknown，没扫到过） |

#### 11.2 坐标系链条：为什么建模时那些名字不能乱起

```
map ──(amcl / slam_toolbox 发布)──▶ odom ──(里程计或仿真发布)──▶ base_footprint ──▶ base_link ──▶ laser_link / imu_link / ...
```


| 变换 | 谁发布 | 作用 |
|---|---|---|
| `map → odom` | `amcl`（已知地图定位）或 SLAM | 修正**长期**漂移：把机器人"拽回"地图上的正确位置 |
| `odom → base_footprint` | 里程计（仿真里的差速插件/控制器） | 提供**短期平滑**的位姿，但会累积漂移 |
| `base_footprint → base_link → 各传感器` | `robot_state_publisher` + URDF | 就是你第六章做的那套模型 |

> 💡 **回到第 7 节的那个决定**：为什么要在模型里加 `base_footprint`、为什么雷达 link 叫 `laser_link`？
>
> 因为 Nav2 的参数文件里全是**按名字**引用坐标系的（`robot_base_frame: base_footprint`、
> `scan_topic: /scan`、`global_frame: map`）。
> **建模阶段把名字定对，导航阶段就只是填参数；名字对不上，就会一直报 TF 错误。**

### 12、用 slam_toolbox 建第一张地图

- **输出**：`/map` 话题

> ⚠️ **`use_sim_time:=True` 必须加**。SLAM 里所有传感器数据都带时间戳，
> 仿真时间和系统时间不一致会导致"数据过期"被丢弃。
> 书中启动日志里还有一条值得注意的警告（说明参数没对齐也没事，但要知道）：
>
> ```

> ```
>
> 即 SLAM 默认按 20 m 的雷达配置，而仿真雷达只有 8 m——**这类"参数比硬件大"的警告不用慌**，
> 但如果反过来（参数比硬件小），就会白丢数据。

**RViz 里看地图**：`Fixed Frame` 改成 `map` → `Add → By Topic → /map`（或加 `Map` 显示项选 `/map`）。
地图会随着机器人走动一点点"长出来"，走到哪里画到哪里。

> 💡 **地图画歪了/糊了，先查这三条**
>
> 1. **里程计**：`odom → base_footprint` 有没有、准不准（差速插件的轮距轮径填错，地图必歪）
> 2. **时间戳**：`use_sim_time` 有没有设对
> 3. **雷达安装位姿**：`laser_link` 在模型里的高度/朝向和实际不符，扫描匹配就会一直错位

书中实测日志：

```
[map_saver]: Free threshold unspecified. Setting it to default value: 0.250000
[map_saver]: Occupied threshold unspecified. Setting it to default value: 0.650000
[map_io]: Received a 376 X 222 map @ 0.05 m/pix
[map_io]: Writing map occupancy data to room.pgm
[map_io]: Writing map metadata to room.yaml
[map_saver]: Map saved successfully
```


产物是**一对文件**：

| 文件 | 内容 |
|---|---|
| `room.pgm` | 灰度图片：像素值表示占据概率。**可以用图片编辑器改**（比如手动补墙） |
| `room.yaml` | 描述文件：分辨率、原点、阈值等 |

`room.yaml` 的字段（书的代码清单 7-5 的结构）：

```yaml
image: room.pgm          # 地图图片文件名
mode: trinary            # 三态：占据/空闲/未知
resolution: 0.05         # 每个像素代表多少米（0.05 = 5cm/像素）
origin: [-7.46, -6.43, 0.0]   # 地图左下角在地图坐标系中的位姿 [x, y, yaw]
negate: 0                # 是否反色（0=白为可走）
occupied_thresh: 0.65    # 大于这个概率算障碍
free_thresh: 0.25        # 小于这个概率算可走
```


> 💡 **`resolution` 和 `origin` 是导航精度的地基**
>
> `resolution` 决定"地图上的 1 像素 = 实际几厘米"，`origin` 决定"地图贴在 `map` 坐标系的哪里"。
> 这两个值错了，机器人会**自信地走错位置**——而且没有任何报错。

### 13、Nav2：安装、参数与启动

#### 13.1 安装

```bash
sudo apt install ros-$ROS_DISTRO-navigation2
sudo apt install ros-$ROS_DISTRO-nav2-bringup     # 官方示例 launch / 参数 / RViz 配置
```


`nav2_bringup` 里那套默认参数**就是给你的起点**，我们的做法是"复制出来改"。

#### 13.2 参数：只需要改三类

```bash
# 建 config / launch / maps / param 目录后，把官方参数复制过来
cp /opt/ros/$ROS_DISTRO/share/nav2_bringup/params/nav2_params.yaml \
   src/fishbot_navigation2/config/
```


打开这个文件会有**几百行**——别怕，它是把所有节点的参数放在一个文件里，每个节点最多几十行。

| 参数类别 | 长什么样 | 怎么改 |
|---|---|---|
| **话题名** | `scan_topic`、`odom_topic` | 和你实际发布的话题对齐（默认 `/scan`、`/odom`，和前面仿真一致就不用改） |
| **坐标系名** | `odom_frame_id`、`robot_base_frame`、`global_frame` | 对齐 `odom`、`base_footprint`、`map` |
| **机器人尺寸** | `robot_radius`、`inflation_radius` | **必须按你的模型填**，见下 |

**机器人半径**（`global_costmap` 与 `local_costmap` 都要改）：

```yaml
local_costmap:
  local_costmap:
    ros__parameters:
      robot_radius: 0.12      # 与建模时的车体半径一致

global_costmap:
  global_costmap:
    ros__parameters:
      robot_radius: 0.12
```


> ⚠️ **半径填错的后果是"看起来玄学"的**
>
> - 填**大**了：窄通道过不去，规划器一直报"无法规划路径"
> - 填**小**了：贴着墙走、**撞上去才发现**
>
> 另外注意：书里默认值写的是 `base_link`，而我们模型里导航的根坐标系是 `base_footprint`，
> 这类名字差异就是 11.2 节强调的"建模时定名字"的价值。

**膨胀层**（inflation）：

```yaml
global_costmap:
  global_costmap:
    ros__parameters:
      plugins: ["static_layer", "obstacle_layer", "inflation_layer"]
      inflation_layer:
        plugin: "nav2_costmap_2d::InflationLayer"
        cost_scaling_factor: 3.0
        inflation_radius: 0.55      # 障碍物向外"膨胀"的半径
```


**AMCL（定位）** 的关键几项：

```yaml
amcl:
  ros__parameters:
    use_sim_time: True
    base_frame_id: "base_link"      # 机器人基坐标系
    odom_frame_id: "odom"           # 里程计坐标系
    global_frame_id: "map"          # 地图坐标系
    robot_model_type: "nav2_amcl::DifferentialMotionModel"   # 差速模型
    max_particles: 2000             # 粒子数：越大越准越慢
    min_particles: 500
```


#### 13.3 launch：把参数喂给 Nav2

`launch/navigation2.launch.py`（书的代码清单 7-10，下面这份已把 OCR 里丢失的括号/引号补全）：

```python
import os

import launch
import launch_ros
from ament_index_python.packages import get_package_share_directory
from launch.launch_description_sources import PythonLaunchDescriptionSource


def generate_launch_description():
    # ① 路径：本包的地图/参数 + nav2_bringup 的 rviz 配置
    fishbot_navigation2_dir = get_package_share_directory('fishbot_navigation2')
    nav2_bringup_dir = get_package_share_directory('nav2_bringup')
    rviz_config_dir = os.path.join(nav2_bringup_dir, 'rviz', 'nav2_default_view.rviz')

    # ② 三个可以在命令行覆盖的 launch 参数：ros2 launch ... map:=xx.yaml
    use_sim_time = launch.substitutions.LaunchConfiguration('use_sim_time', default='true')
    map_yaml_path = launch.substitutions.LaunchConfiguration(
        'map', default=os.path.join(fishbot_navigation2_dir, 'maps', 'room.yaml'))
    nav2_param_path = launch.substitutions.LaunchConfiguration(
        'params_file', default=os.path.join(fishbot_navigation2_dir, 'config', 'nav2_params.yaml'))

    return launch.LaunchDescription([
        launch.actions.DeclareLaunchArgument(
            'use_sim_time', default_value=use_sim_time,
            description='Use simulation (Gazebo) clock if true'),
        launch.actions.DeclareLaunchArgument(
            'map', default_value=map_yaml_path,
            description='Full path to map file to load'),
        launch.actions.DeclareLaunchArgument(
            'params_file', default_value=nav2_param_path,
            description='Full path to param file to load'),

        # ③ 关键：复用官方 bringup_launch.py，只把我们自己的参数"塞"进去
        launch.actions.IncludeLaunchDescription(
            PythonLaunchDescriptionSource(
                [nav2_bringup_dir, '/launch', '/bringup_launch.py']),
            launch_arguments={
                'map': map_yaml_path,
                'use_sim_time': use_sim_time,
                'params_file': nav2_param_path,
            }.items()),

        # ④ 顺手开 RViz（带 Nav2 专用面板）
        launch_ros.actions.Node(
            package='rviz2',
            executable='rviz2',
            name='rviz2',
            arguments=['-d', rviz_config_dir],
            parameters=[{'use_sim_time': use_sim_time}],
            output='screen'),
    ])
```


> 💡 **这个 launch 的写法值得学**：它**没有**一个个去 `Node(...)` 起 Nav2 的十几个节点，
> 而是 `IncludeLaunchDescription` 复用官方的 `bringup_launch.py`，只覆盖三个参数。
> 官方升级/换仿真器时，你的 launch 基本不用改。

别忘了把三个目录装进 install：

```cmake

```

### 14、导航应用开发：用代码接管导航

RViz 点一下很爽，但真实项目里导航要由**程序**驱动。这一节按"初始化位姿 → 拿实时位置 → 发目标点"三步走。

#### 14.1 初始化位姿（不用手点 RViz）

**方式一：命令行发话题**（书的代码清单 7-16）

```bash
ros2 topic pub /initialpose geometry_msgs/msg/PoseWithCovarianceStamped \
"{header: {frame_id: map}, pose: {pose: {position: {x: 0.0, y: 0.0, z: 0.0}, orientation: {w: 1.0}}}}" --once
```


AMCL 相关的话题与服务（书的代码清单 7-15 要点）：

| 名字 | 类型 | 用途 |
|---|---|---|
| `/initialpose` | 话题 `PoseWithCovarianceStamped` | 告诉 AMCL "我大概在这" |
| `/amcl_pose` | 话题 `PoseWithCovarianceStamped` | AMCL 估计出的当前位姿 |
| `/request_nomotion_update` | 服务 | 强制重算一次位姿（站着不动时用） |

**方式二：用 `nav2_simple_commander`**（官方 Python 高层封装，推荐）

```python
from geometry_msgs.msg import PoseStamped
from nav2_simple_commander.robot_navigator import BasicNavigator
import rclpy


def main():
    rclpy.init()
    navigator = BasicNavigator()

    # 造一个"初始位姿"：坐标系必须是 map
    initial_pose = PoseStamped()
    initial_pose.header.frame_id = 'map'
    initial_pose.header.stamp = navigator.get_clock().now().to_msg()
    initial_pose.pose.position.x = 0.0
    initial_pose.pose.position.y = 0.0
    initial_pose.pose.orientation.w = 1.0

    navigator.setInitialPose(initial_pose)      # 等价于 RViz 的 2D Pose Estimate
    navigator.waitUntilNav2Active()             # 等 Nav2 完全就绪
    rclpy.shutdown()
```


> 💡 `setInitialPose` 内部**还是发 `/initialpose` 话题**（书的 7-18 节翻了源码），
> 高层封装只是替你写好了消息构造和坐标系设置。

#### 14.2 用 TF 拿机器人实时位置

因为 AMCL 会持续发布 `map → base_footprint`，所以"查机器人在地图上的位姿"就是查一条 TF：

```python
import rclpy
from rclpy.node import Node
from tf2_ros import Buffer, TransformListener
from rclpy.time import Time

class RobotPose(Node):
    def __init__(self):
        super().__init__('get_robot_pose')
        self.buffer = Buffer()
        self.listener = TransformListener(self.buffer, self)
        self.timer = self.create_timer(1.0, self.on_timer)

    def on_timer(self):
        try:
            # 拿 map → base_footprint：结果就是机器人在地图坐标系里的位姿
            tf = self.buffer.lookup_transform('map', 'base_footprint', Time())
            t = tf.transform.translation
            self.get_logger().info(f'当前位姿: x={t.x:.2f}, y={t.y:.2f}')
        except Exception as e:
            self.get_logger().warn(f'还没准备好: {e}')

def main():
    rclpy.init()
    rclpy.spin(RobotPose())
```


这和第五章 5.x 节那段 TF 监听代码是**同一个套路**，只是坐标系换成了 `map → base_footprint`。

#### 14.3 发目标点：单点导航

**底层是动作（action）**，可以先看一眼：

```bash
ros2 action list | grep -i navigate        # 会看到 /navigate_to_pose
ros2 action info /navigate_to_pose
ros2 interface show nav2_msgs/action/NavigateToPose
```


命令行直接发一个目标点（书的代码清单 7-25/7-24 的形式）：

```bash
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
"{pose: {header: {frame_id: map}, pose: {position: {x: 2.0, y: 2.0, z: 0.0}, orientation: {w: 1.0}}}}" --feedback
```


**用 Python 写就是十几行**（书的代码清单 7-26，补全了 OCR 丢掉的下划线）：

```python
from geometry_msgs.msg import PoseStamped
from nav2_simple_commander.robot_navigator import BasicNavigator, TaskResult
import rclpy
from rclpy.duration import Duration


def main():
    rclpy.init()
    navigator = BasicNavigator()

    # ① 等 Nav2 就绪（AMCL 有初始位姿、各个 server 都 active）
    navigator.waitUntilNav2Active()

    # ② 造目标点
    goal_pose = PoseStamped()
    goal_pose.header.frame_id = 'map'
    goal_pose.header.stamp = navigator.get_clock().now().to_msg()
    goal_pose.pose.position.x = 1.0
    goal_pose.pose.position.y = 1.0
    goal_pose.pose.orientation.w = 1.0

    # ③ 发目标，边跑边看反馈
    navigator.goToPose(goal_pose)
    while not navigator.isTaskComplete():
        feedback = navigator.getFeedback()
        navigator.get_logger().info(
            f'预计 {Duration.from_msg(feedback.estimated_time_remaining).nanoseconds / 1e9:.1f} s 后到达')
        # 超时自动取消（防止机器人卡在某个角落一直磨）
        if Duration.from_msg(feedback.navigation_time) > Duration(seconds=600.0):
            navigator.cancelTask()

    # ④ 看最终结果
    result = navigator.getResult()
    if result == TaskResult.SUCCEEDED:
        navigator.get_logger().info('导航结果：成功')
    elif result == TaskResult.CANCELED:
        navigator.get_logger().warn('导航结果：被取消')
    elif result == TaskResult.FAILED:
        navigator.get_logger().error('导航结果：失败')
    else:
        navigator.get_logger().error('导航结果：返回状态无效')


if __name__ == '__main__':
    main()
```


| API | 作用 |
|---|---|
| `waitUntilNav2Active()` | 等 Nav2 全部就绪（省掉自己轮询生命周期） |
| `setInitialPose(pose)` | 初始化位姿 |
| `goToPose(pose)` | 单点导航（内部 `send_goal_async` 到 `/navigate_to_pose`） |
| `isTaskComplete()` | 任务是否结束 |
| `getFeedback()` | 进度反馈：剩余时间、已耗时、剩余距离、当前位姿 |
| `cancelTask()` | 取消（超时兜底必备） |
| `getResult()` | 最终结果：`SUCCEEDED` / `CANCELED` / `FAILED` |

#### 14.4 发一串点：路点导航（巡检的基础）

路点导航的底层动作是 `/follow_waypoints`：

```bash
ros2 action list | grep -i waypoint
ros2 interface show nav2_msgs/action/FollowWaypoints
```


代码上和单点几乎一样，只是把**一个点换成一串点**：

```python
# 造一串路点（PoseStamped 列表）
waypoints = []
for (x, y) in [(1.0, 0.0), (1.0, 1.0), (0.0, 1.0)]:
    p = PoseStamped()
    p.header.frame_id = 'map'
    p.header.stamp = navigator.get_clock().now().to_msg()
    p.pose.position.x = x
    p.pose.position.y = y
    p.pose.orientation.w = 1.0
    waypoints.append(p)

navigator.followWaypoints(waypoints)     # 依次跑完全部路点
while not navigator.isTaskComplete():
    feedback = navigator.getFeedback()
    navigator.get_logger().info(f'正在前往第 {feedback.current_waypoint + 1} 个路点')
```


> 💡 **单点 vs 路点：什么时候用哪个**
>
> - **单点**：用户点一个目标就走（送快递、点哪走哪）
> - **路点**：固定线路循环（**巡检、巡逻、仓库盘点**）——因为可以循环发路点，天然支持"跑完一圈再来一圈"

### 15、综合实践：自动巡检机器人（书 7.5 的思路）

> ⚠️ 这一节书中依赖真机/仿真 + 语音库（`espeak`），本文**只给架构与骨架**，不给完整可运行代码。

把前面所有零件拼起来，一个"自动巡检机器人"就是：

```
   ┌──────────────┐  路点列表   ┌────────────────┐
   │  巡检控制节点 │──────────▶│  Nav2（路点导航）│──▶ 机器人按序走点
   └──────┬───────┘            └────────────────┘
          │ 到点后触发
          ├──▶ 语音播报（espeak）："已到达 3 号点位，设备正常"
          └──▶ 图像记录（订阅 /camera/image_raw，存盘 / 上传）
```


| 模块 | 用到的技术 | 出自本文哪一节 |
|---|---|---|
| 让车能动 | Gazebo + 差速插件 / ros2_control | §9、§10 |
| 建图 | `slam_toolbox` + `map_saver_cli` | §12 |
| 会走路 | Nav2 + 参数 + launch | §13 |
| 按线路走 | `followWaypoints` | §14.4 |
| 到点动作 | 订阅反馈 / 到点回调 → 语音、拍照 | 本章 |

**关键设计点**：把"路点 + 每个点要干什么"做成**配置**（YAML/JSON），
而不是把坐标写死在代码里——这样换一条巡检线路不用改程序，只改配置。

> 💡 **走到这一步，你已经具备的能力**
>
> 建模（URDF/Xacro）→ 加物理属性 → 进仿真 → 接 ros2_control → 建图 → 地图上导航 → 用代码驱动。
> 这套链路和真实项目里"仿真验证 → 真机部署"的顺序是**一致**的：
> 因为控制器和接口都标准化了（§10），仿真调好的逻辑搬到真机上，主要改的就是硬件接口那一层。
